# Внешняя проверка приёмки

[English](acceptance-gate.md)

Контракт владельца проекта позволяет сделать заданные проверки условием успеха
запуска. После генерации проверка выполняется в официальной Windows-песочнице
Codex. Она не вызывает модель, не выполняет вход, не использует шлюз подписки и
не исправляет ошибки. Автоматического поиска доверенного проверяющего кода нет.

## 1. Задайте доверенные проверки

Перед использованием изучите контракт и единственный самодостаточный Python-файл
проверки. Он должен лежать рядом с контрактом; имя задаётся относительным путём
к `.py`. Контракт содержит ровно следующие поля:

```json
{
  "schema": 1,
  "checker": "verifier.py",
  "inputs": ["sum_cli.py"],
  "min_checks": 3,
  "timeout_s": 30
}
```

`inputs` — непустой список файлов или каталогов относительно корня проекта,
содержимое которых связывается с проверкой. Корень проекта, `.git`, `.codex-flow`,
`.tmp` и `.home` исключены. Указывайте конкретные исходные файлы с ограниченным
объёмом. `min_checks` — целое число от 1 до 1000; `timeout_s` — от 1 до 300.
Логические значения не считаются целыми числами в этом контракте.
В путях контракта используйте `/`, в том числе в Windows. Абсолютные пути,
переходы к родителю, повторные входы, ссылки и reparse points отклоняются.

До генерации среда загружает и фиксирует контракт и проверяющий код в защищённом
снимке `.codex-flow`. Изменение контракта или проверяющего кода отклоняется.
Хеши входных файлов сверяются до и после проверки; изменение отменяет приёмку.
Оба списка хешей сохраняются отдельно в `acceptance-inputs.json`; запись о приёмке
связана с этим файлом через `input_inventory_sha256`.
На хосте читаются метаданные и хеши; проверяющий код и созданное приложение
никогда не импортируются и не запускаются на хосте.

## 2. Проверьте метаданные, затем запустите проверку

Из каталога Codex Flow можно изучить комплектный пример без выполнения кода:

```powershell
python codex-flow.py --repo examples/acceptance-gate verify --acceptance-file examples/acceptance-gate/contract.json
```

По умолчанию `verify` проверяет только метаданные. С `--execute` заданная проверка
выполняется в официальной песочнице, без генерации и входа по подписке:

```powershell
python codex-flow.py --repo examples/acceptance-gate verify --acceptance-file examples/acceptance-gate/contract.json --execute --timeout 30
```

Для рабочего проекта явно передайте контракт, проверенный владельцем:

```powershell
python codex-flow.py --repo C:\work\project run "Выполни согласованное изменение" --enable --acceptance-file C:\checks\project\contract.json --timeout 180
```

Глобальные параметры, включая `--repo` и `--codex`, стоят перед подкомандой.
В `run` и `verify` можно повторять `--protect-path C:\existing\private`;
каждый путь должен уже существовать. Эти пути добавляются в запреты чтения
песочницы. Схема конфигурации проекта не меняется.

Лимит `run --timeout` включает генерацию и проверку приёмки. Тайм-аут контракта
задаёт дополнительный предел в рамках оставшегося времени задачи. Новый отдельный
срок проверке не выдаётся. Отмена или исчерпание времени отменяет приёмку.

## 3. Реализуйте интерфейс проверки

Песочница запускает зафиксированный код абсолютным путём к Python:

```text
python -I -B SNAPSHOT/checker.py --workspace WORKSPACE --report SCRATCH/report.json --nonce RUNNONCE
```

Текущий каталог — новое временное пространство. Проект и снимок доступны только
для чтения; временное пространство доступно для записи. Временные файлы и вывод
размещайте в нём. Проверяющий код должен создать новый JSON-отчёт в UTF-8
ровно следующей структуры:

```json
{
  "schema": 1,
  "nonce": "значение из --nonce",
  "checks": [
    {"id": "cli.sum", "status": "passed"},
    {"id": "cli.negative", "status": "passed"},
    {"id": "cli.invalid", "status": "passed"}
  ]
}
```

Идентификаторы проверок уникальны. Допустимые статусы: `passed`, `failed`,
`skipped`. Для приёмки нужны код выхода 0, не менее `min_checks` проверок и статус
`passed` у каждой. Пустой отчёт, пропуски, ненулевой код выхода, отсутствующий,
устаревший, некорректный или слишком большой отчёт, несовпадение nonce или хешей,
тайм-аут, отмена и неполный захват вывода приводят к отказу в приёмке.
Текст stdout, заявление модели о завершении и один код выхода 0 недостаточны.

Каждая запись должна соответствовать реальному заданному утверждению. Если
проверяющий код запускает unittest, проверяйте результат в структурированном виде
и положительное значение `testsRun`; ноль собранных тестов означает отказ.
Успешного запуска процесса unittest для этого недостаточно.

## 4. Учитывайте границы результата

Без `--acceptance-file` завершённая генерация остаётся `completed_unverified`
с `accepted: false`. Успех всех настроенных проверок позволяет получить
`completed_verified` с `accepted: true`. Отказ настроенной проверки приёмки
возвращает код выхода `3`. Автоматических исправлений и повторов проверки нет.

Результат подтверждает только доверенные проверки, заданные владельцем. Он не
подтверждает полное покрытие, качество 100/100 или корректность произвольного
проверяющего кода. Недобросовестный код может выдумать результаты; перед доверием
к заключению изучите его логику и происхождение.

Сеть отключена. Настоящие каталоги `.codex` и `.agents`, существующее дерево
`.codex-flow/native-state` проекта и явно защищённые пути запрещены.
Переменные окружения с учётными данными удаляются, HOME/TMP
указывают на собственное временное пространство. Это не доказывает полную изоляцию
чтения хоста: профили разрешений и общее состояние Windows-песочницы сохраняют
ограничения платформы. При тайм-ауте выполняется попытка завершить дерево
процессов; независимого доказательства завершения каждого потомка нет.

Проверка приёмки не доказывает преимущество роя агентов. Текущая роль
`reviewer/high` — независимая оценка рисков приёмки; прежние результаты не
подтверждают, что команда более компактных моделей ускоряет разработку
без снижения качества.
