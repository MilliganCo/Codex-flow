# Долговечные workflow проекта

[English](workflows.md)

Команда `workflow` сохраняет прогресс четырёх этапов:
`prepare → generate → verify → report`. Существующие команды `run`, `verify`,
`runs` и `benchmark` сохраняют своё отдельное поведение.

## 1. Настройте проверки и проверьте задачу

Запускайте из каталога Codex Flow. Глобальные параметры указываются до `workflow`:

```powershell
python codex-flow.py --repo C:\work\project workflow init --dry-run --json
python codex-flow.py --repo C:\work\project workflow init
python codex-flow.py --repo C:\work\project workflow start "Внеси согласованное изменение" --dry-run --human --lang ru
```

`workflow init` поддерживает существующий Git-проект с тестами Python `unittest`.
Автоопределение ищет сначала в `tests/`, затем в `test/` файлы `test*.py`
с импортами unittest. Оно читает синтаксические деревья Python, не импортирует
модули проекта, не собирает и не запускает тесты, проверяющий или модели.
Успешная настройка не подтверждает прохождение тестов. `--dry-run` показывает
план настройки без записи файлов; `--json` включает машинный формат результата.

Другой существующий каталог тестов можно указать явно:

```powershell
python codex-flow.py --repo C:\work\project workflow init --framework unittest --tests qa/unit --pattern "test_*.py" --dry-run
```

Путь вроде `qa/unit` задаётся относительно проекта, с разделителями POSIX;
шаблон относится только к имени файла. Явный выбор unittest не требует маркера
импорта для автоопределения. Для других систем тестирования нужен явно выбранный
и проверенный владельцем `--acceptance-file C:\checks\contract.json`. Формат
описан в [контракте приёмки](acceptance-gate.ru.md).

Настройка создаёт версию `.codex-flow/project/v/REVISION/` с файлами `checker.py`,
`acceptance.json`, `task.md` и `setup.json`. Указатель активной версии выбирает
контракт по умолчанию. После такой явной настройки `workflow start` допускает
запуск без `--acceptance-file`; без настройки или явного контракта команда
останавливается. Переданный `--acceptance-file` по-прежнему выбирает этот
проверенный контракт. Настройка не меняет маршрутизацию моделей, разрешение
запуска проекта или глобальные параметры.

Повторный init с теми же параметрами сохраняет существующую версию и правки
задачи. Изменение параметров или созданного проверяющего требует проверки
и `workflow init --refresh`: команда создаёт новую версию, сохраняя старые файлы.
Refresh фиксирует текущие байты исходных тестов и явно заменяет прежний набор
их хешей. Сохраните внесённый текст задачи перед использованием нового шаблона.

Созданный проверяющий фиксирует SHA-256 существующих выбранных тестовых файлов.
Удаление или изменение такого файла проваливает приёмку; добавлять новые
тестовые файлы разрешено. По умолчанию пропуски запрещены. Для явно проверенного
допуска есть `--allow-skips N`, от 0 до 800: ограничивается число пропущенных
тестов и событий пропуска, включая subtest. Пропуски не считаются успехом;
хотя бы один настоящий тест должен пройти. Нулевой набор, только пропущенные
тесты, ошибки импорта, failures, errors, expected failures и unexpected successes
проваливают приёмку. Сбор ограничен 800 тестами, отчёт — 64 КиБ.
Эти проверки подтверждают обычные результаты unittest, но не защищают
от намеренной подделки свидетельств самим Python-кодом тестов.

Передайте текст задачи либо `--task-file C:\checks\task.md`. Чтобы использовать
созданный файл задачи, откройте путь из результата init, замените заготовку
на нужное изменение и удалите `CODEX_FLOW_TASK_REQUIRED`. Неизменённый шаблон
отклоняется. Dry run команды start читает локальные входы без генерации и запуска
проверяющего.

Для выполнения нужны существующий Git-проект, Python 3.11+ и установленный
нативный Codex CLI. Генерация использует существующий вход по подписке.
Для проверки нужна рассмотренная официальная командная песочница Codex в Windows.
Workflow не устанавливает зависимости, не меняет глобальные настройки и не
подключает платный API как запасной маршрут.

## 2. Запустите с фиксированным бюджетом

```powershell
python codex-flow.py --repo C:\work\project workflow start --task-file C:\checks\task.md --enable --timeout 1200 --max-model-requests 40
```

Для выполнения нужен `--enable` либо включённая конфигурация проекта.
`--timeout` принимает 1–3600 секунд активной работы, `--max-model-requests` —
1–80 физических запросов на инференс. Лимиты фиксируются при создании.
Необязательный `--execution-contract C:\checks\execution.json` фиксирует явно
выбранную схему выполнения, без дополнительных прав или бюджета.

По умолчанию используется одна генерация Sol. Необязательные режимы Luna
остаются экспериментальными: живой проверки для этого workflow нет.
Текущие свидетельства получены на явно обозначенных тестовых исполнителях;
вызовы моделей остаются на паузе. Успех фикстуры не доказывает выигрыш качества
или производительности.

[Каталог ролей моделей](model-roles.ru.md) доступен только для чтения и включает
Terra как кандидата с отключённым запуском. Просмотр не вызывает инференс
и не проверяет доступ аккаунта:

```powershell
python codex-flow.py --repo C:\work\project workflow models --json
```

Записи каталога не меняют маршрутизацию и не возобновляют живые эксперименты.

## 3. Посмотрите состояние, приостановите или продолжите

Используйте ID из результата запуска:

```powershell
python codex-flow.py --repo C:\work\project workflow status WORKFLOW_ID --human --lang ru
python codex-flow.py --repo C:\work\project workflow status WORKFLOW_ID
python codex-flow.py --repo C:\work\project workflow pause WORKFLOW_ID
python codex-flow.py --repo C:\work\project workflow resume WORKFLOW_ID --enable
python codex-flow.py --repo C:\work\project workflow cancel WORKFLOW_ID
```

`--human` показывает краткое состояние, попытки этапов, остаток запросов
и активного времени, а также приёмку сохранённого снимка. `--lang ru` или
`--lang en` выбирает язык подписей; по умолчанию — русский. Эти параметры
доступны и для start, pause, resume, cancel. Без `--human` существующий
JSON-интерфейс этих команд не меняется. Текстовый результат сообщает
о нарушенной целостности и изменении исходников, не приписывая приёмку текущему
исходному проекту.

Pause и cancel сохраняют управляющий запрос. Активная операция останавливается
после его обработки. Время паузы не расходует бюджет активной работы.
Для resume нужен `--enable` либо включённая текущая конфигурация проекта.
Выключение проекта останавливает новые запуски CLI; сохранённые параметры сами
по себе не разрешают новый вызов модели.
Заменить бюджеты, задачу, проверяющий или контракт выполнения через resume нельзя.
Отмена окончательна. Завершённый workflow сохраняет исходные свидетельства.

Resume повторно сверяет зафиксированные входы, идентичность runtime, сохранённые
результаты и хеши файлов. Корректный завершённый этап используется повторно.
На этап допускается не более двух попыток через явный запуск или resume;
автоматического цикла повторов workflow и автоматического повтора модели/HTTP 429
нет. Семантический провал неизменённой проверки окончателен. Прерванные попытки
сохраняются в отдельных каталогах. Исчерпанный бюджет или лимит попыток требует
отдельно согласованной новой задачи.

## 4. Учитывайте устройство файлов и состояния

Состояние находится в `.codex-flow/workflows/`. SQLite `state.sqlite` — основной
источник данных об этапах, управлении, владельце, запросах и расходе времени.
JSON-результаты и трассы служат диагностике: их правка не даёт прав, не возвращает
бюджет и не может сделать этап принятым.

`prepare` сохраняет текущие байты отслеживаемых Git-файлов и неигнорируемых новых
файлов, включая несохранённые в коммит изменения. Удалённые из рабочей папки
отслеживаемые файлы отсутствуют в снимке. Игнорируемые зависимости не обходятся.
Исключены каталоги `.git`, `.codex-flow`, `.codex`, `.agents`, `.home`, `.tmp`
и имена файлов учётных данных: `.env`, `.env.*` кроме `.env.example`,
`auth.json`, `credentials.json`, `*.key`, `*.pem`.

Снимки отклоняют ссылки, reparse points, обычные файлы с несколькими hardlink,
выход за границы, алиасы регистра, имена устройств Windows и имена с точкой или
пробелом в конце. Пределы: 10 000 файлов, 256 МиБ суммарно и 64 МиБ на файл;
превышение приводит к явной ошибке. Манифест связывает относительные пути,
SHA-256, размер и, где поддерживается, исполняемый бит POSIX.
Целостность исходников и снимков проверяется повторно.

`generate` получает замороженный снимок в новом каталоге попытки. Локальные
Git-метаданные создаются с пустыми шаблонами, отключёнными hooks и fsmonitor.
Команды метаданных не запускают checkout-фильтры, textconv или хуки проекта.
Workflow не переносит сгенерированные изменения в исходный проект.

`verify` запускает зафиксированный проверяющий через официальную командную
песочницу. Рабочая папка попытки доступна для чтения, отдельный scratch — для
записи. Хост не импортирует и не исполняет код сгенерированного приложения или
проверяющего. Провал проверки, недостоверные свидетельства, изменение файлов
или исчерпанный бюджет исключают приёмку.

`report` создаёт пакет: точное полное дерево результата в `files/`, файлы
`manifest.json`, `seed-manifest.json`, `diff.patch`, `report.json`. Отчёт перечисляет
добавленные, изменённые и удалённые пути. Вход и выход текстового diff ограничены
1 МиБ на файл, весь diff — 8 МиБ. Крупные и бинарные файлы, а также исчерпание
места в diff обозначаются краткими отметками; это фиксирует `text_diff_limited`.
Точные байты результата всегда остаются в `files/` вместе с хешами манифеста.
Diff предназначен для просмотра; его применимость как патча не гарантируется.
Патч к исходному проекту не применяется.

## 5. Правильно трактуйте бюджет и восстановление

Каждый физический запрос модели резервируется в постоянном хранилище до отправки.
Неудачные, неизвестные и прерванные запросы расходуют резерв; resume его не
обнуляет. Известные данные usage уточняют свидетельства, но не возвращают резерв.

Активное время резервируется квантами по 30 секунд с heartbeat каждые 5 секунд.
При штатной работе учитывается наблюдаемое время. После падения владельца
неизвестный остаток кванта списывается консервативно; перезапуск не возвращает его.

В проекте одновременно работает один владелец workflow: PID связан со временем
создания процесса. Восстановление блокируется, пока владелец или зарегистрированный
дочерний процесс может быть жив, включая неизвестное состояние. Чужие процессы
не завершаются. Перед новым resume выясните состояние записанного владельца.

`accepted` подтверждает выбранные владельцем проверки для сохранённого пакета.
Это не подтверждает их прохождение на текущем исходном проекте.
`source_project_updated` остаётся false; поле отчёта `source_changed_since_start`
показывает независимые изменения исходников после снимка. `backend_kind`
отличает тестового исполнителя от нативного выполнения.

Это принадлежащие workflow каталоги снимков, а не Git worktree. Они не доказывают
полную конфиденциальность чтения хоста, завершение всех потомков, полноту покрытия
или выигрыш скорости и качества. Сохраняются
[ограничения изоляции платформы](safety-and-permissions.md).

## Проверенные контроли восстановления

[Два контроля реальной аварии](../benchmarks/workflow-recovery-20261027/README.ru.md)
прошли с переносимым фиктивным генератором без модели и настоящим Windows SDK.
Каждый workflow сохранил один вызов генератора и один резерв запроса после resume;
все восемь проверок прошли. Продолжение только отчёта не вызвало SDK повторно.
Независимая ручная правка исходного проекта сохранилась.

Незакрытое намерение запуска блокирует восстановление даже после смерти владельца.
Оно не снимается угадыванием PID или завершением чужих сессий. Короткие внутренние
пути попыток уменьшают рост путей Windows launcher.
