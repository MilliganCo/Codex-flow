# Протокол A/B/Ablation — Codex-flow против Sol 6.1 XHigh

**Принцип:** оценка проектируется **до** создания решений. Основной вопрос: даёт ли Codex-flow с Mercury, Harness² и многоагентной схемой прирост **полезной работы за время и квоту**, не теряя качество по сравнению с одиночным Sol 6.1 XHigh.

## 1. Фиксация до старта

Сохранить неизменяемый `experiment-manifest.json` со значениями: `experiment_id`, timestamp, SHA256 `TREE_BENCHMARK_TASK.md`, SHA исходного scaffold, версия CLI, модель/effort, OS/CPU/RAM, терминал, backend/auth class (без секретов), лимиты времени/вызовов/агентов, доступные dependencies, валидатор/rubric SHA, начальный run order, календарная дата. Все изменения условий — отдельный новый experiment ID. Избегать отдельных подсказок, которые улучшают только одну ветку.

Задача единая; baseline и full читают одинаковые тексты, в том числе разрешение на Python/другие зависимости и описание 4D. Baseline выполняется обычным Codex **без** Codex-flow, Mercury, Harness² и subagents. Candidate использует Codex-flow, но главный модельный профиль Sol XHigh тот же, что и в A.

**Обязательные группы:**

| ID | Main model | Multi-agent | Mercury | Harness² | Назначение |
|---|---|---|---|---|---|
| A | Sol 6.1 XHigh | нет | нет | нет | одиночный baseline |
| B | Sol 6.1 XHigh | да, ≤3 | реальный adapter | реальный guarded loop | полный flow |
| C | Sol 6.1 XHigh | да, ≤3 | да | нет | польза Harness² |
| D | Sol 6.1 XHigh | да, ≤3 | нет | да | польза Mercury |
| E (опция) | Sol 6.1 XHigh | нет | да | да | польза подагентов |

`real` означает подтверждённые вызовы/trace. Если нет доступа к компоненту, B проходит только как `degraded experiment`, и сравнение нельзя подписывать «Mercury+Harness² vs solo».

## 2. Процедура

1. Вынести скрытые дополнительные тесты (`evaluator/`) в отдельную контролируемую директорию, недоступную обоим исполнителям, заморозить их SHA256 до старта.
2. Выделить чистые независимые worktrees A и B из одного scaffold-коммита. Отдельные HOME/CODEX_HOME/temporary profiles, memory paths, telemetry, .venv, output, logs. Сохранять подписочную auth безопасно: используем штатный login без копирования токенов в репозиторий. При технических ограничениях изоляции зафиксировать это и ослабить выводы.
3. Создать wrapper, который запускает подписочный Codex на выбранной модели/effort, собирает timestamp/status/events и завершает по одинаковому safety budget. Передать `TREE_BENCHMARK_TASK.md` как **дословно одинаковый промпт**. Проверить, что модель действительно `gpt-6.1-sol` и `xhigh` согласно инструменту, а не только названию профиля.
4. Запустить A и B параллельно как просил владелец. Сохранить PID/start UTC/end UTC, события, exit code, промежуточные артефакты, CPU/RAM spikes, rate limiting, ошибки VPN/соединений.
5. Не давать B доступ к файлам A и наоборот. Если одна ветка закончила первой, не передавать решение второй. Не менять рубрику под результат.
6. После завершения обеих веток запустить **один** независимый evaluator + одинаковые headless тесты + ручной визуальный просмотр. До оценки спрятать имена стратегий (`solution-1/2`).
7. После первичного A/B — абляции C и D в свежих worktrees с тем же заданием. Контролировать версию Codex-flow. Абляции включать в бюджет и время эксперимента.
8. Для более честного latency-вывода сделать ещё 1–2 повторения с разным порядком и раздельным временем запуска, если подписочная квота позволит. Параллельный запуск сам по себе чувствителен к конкурентному использованию CPU, сети и quota/rate-limit.
9. Финальные исходники сохранять в versioned artifacts или отдельные архивы; не сливать лучшие куски двух решений в ходе бенчмарка.

## 3. Независимая шкала качества (100 баллов)

Ниже **максимальные** баллы; оценщик должен хранить для каждого пункта `score`, `max`, `evidence`, `status` (pass/partial/fail/not-assessed), `reason`.

| Категория | Баллы | Верификация |
|---|---:|---|
| 2D: генерируемое ветвистое дерево, детерминизм | 12 | tests + кадры |
| 3D: реальные XYZ, вращение, глубина, occlusion | 13 | математика + tests + кадры |
| 4D: XYZW, W не константа, XW/YW/ZW rotation, 4D→3D→2D | 20 | геометрия + tests + два угла |
| UX: переключение без перегенерации, управление, help, экспорт | 12 | интерактивный smoke |
| Эстетика: органичный вид, крона, ветви, shading | 12 | слепая оценка двух кадров |
| Надёжность: resize, Ctrl+C, headless, маленькое окно, без crashes | 10 | e2e/smoke |
| Тесты: покрытие ключевых функций, повторяемость | 9 | test output |
| Поддерживаемость: модульность, качество кода, зависимостей | 7 | независимый review |
| README: реальная установка, commands, explanation of 4D | 5 | manual |
| **ИТОГО** | **100** | |

**Критическое условие:** наличие правильного 4D нельзя компенсировать косметикой. `accepted` при score ≥ 80 **и** pass 4D coordinate/rotation/projection **и** приложение запускается. Высокая скорость незавершённого варианта не выигрывает у рабочего. Если ни один не набрал порог, report `no accepted solution`.

Эстетический тест не должен подменять инженерные проверки. При недостатке данных в результате `not-assessed`, а не автоматическое 0/100.

На каждую ветку и каждый прогон:

```json

  "status": "accepted|rejected|partial|failed|degraded",
  "task_sha256": "sha256",
  "scaffold_sha": "git-sha",
  "model_root": "gpt-6.1-sol",
  "effort_root": "xhigh",
  "wall_clock_s": null,
  "time_to_first_working_demo_s": null,
  "setup_s": null,
  "planning_s": null,
  "execution_s": null,
  "refinement_s": null,
  "evaluation_s": null,
  "agent_count": null,
  "peak_concurrent_agents": null,
  "mercury_real_calls": null,
  "harness2_real_probes": null,
  "tool_calls": null,
  "retries": null,
  "failed_calls": null,
  "input_tokens": null,

```

`null` означает неизвестное значение (в UI — `n/a`). Ноль означает действительно измеренный ноль. При подписке вычислять деньги по условным тарифам API как «фактически потрачено» запрещено. Можно отдельную колонку `estimated_api_equivalent_cost_usd` с явно описанной методикой, **но не смешивать** её с оплаченной стоимостью и подписочной квотой.

Дополнительно полезны: p50/p95 при достаточном числе повторов, число файлов, LOC, source complexity, rate-limit incidents, peak RSS, latency per model, число исправленных дефектов, integration overhead, invalid routing, useless agent fan-outs, число конфликтов Git, время rollback. Записывать стоимость external provider только при наличии подтверждённого usage/billing.

## 5. Правила вывода

- Сравнивать `wall_clock_s` можно только для **принятых** решений одинакового объёма. Если B меньше времени, но нет 4D, это не ускорение выполнения задачи.
- Не считать успешные тесты B, которые B сам написал, единственным подтверждением: используется независимый evaluator, созданный до начала эксперимента.
- Один эксперимент не доказывает устойчивый прирост. В отчёте различай `case study` и серию с повторами, записывай условия.
- Harness² refinements и стоимости probes входят в B; не вычитать их из времени/расходов.
- Параллельный A/B запуск — для независимости и наблюдения; отдельные последовательные повторы — для более надёжной оценки производительности.
- Если у Mercury в B фактически 0 успешных вызовов, сравнивание с D не измеряет ценность Mercury.
- Аналогично, если Harness² не изменил/adopted стратегию, это ещё не доказательство бесполезности, а измерение текущей реализации/задачи.
